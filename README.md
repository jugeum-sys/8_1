# 과제 08 - 최소 비용 신장 트리 알고리즘 비교

`gcc -O2 -o mst_compare mst_compare.c` 로 컴파일한다.
실행하면 난수 시드를 묻고, Enter를 누르면 기본 시드(12345)로 아래 결과가 재현된다.

연결 그래프를 보장하기 위해 먼저 신장 트리(간선 49개)를 만들고 목표 간선 수까지 임의의 간선을 더했다. 실행시간은 MST 계산 구간만 재되, 한 번이 수 마이크로초라 1000회 반복 평균을 μs로 환산했다. Kruskal의 간선 수집·정렬·Union-Find 초기화도 알고리즘의 일부라 측정에 포함했다.

## 측정 결과 (시드 12345, 정점 50개)

| | Case 1 희소-리스트-Kruskal | Case 2 밀집-리스트-Kruskal | Case 3 희소-행렬-Prim | Case 4 밀집-행렬-Prim |
|---|---|---|---|---|
| 간선 수 | 100 | 600 | 100 | 600 |
| MST 간선 | 49 | 49 | 49 | 49 |
| MST 비용 | 1,293 | 227 | 1,293 | 227 |
| 메모리 | **6,408 B** | 34,408 B | 10,604 B | **10,604 B** |
| 실행시간 | **2.49 μs** | 15.70 μs | 4.96 μs | **5.53 μs** |

같은 그래프에 대해 Kruskal과 Prim의 비용이 1,293과 227로 정확히 일치했다. 선택된 간선 구성은 달라도 최소 비용은 같아야 한다는 성질이 확인된다. 밀집 그래프의 비용이 훨씬 작은 이유는 간선이 6배 많아 작은 가중치를 고를 여지가 그만큼 넓기 때문이다.

## 분석

**메모리: 리스트는 간선 수에 비례, 행렬은 고정.** 인접 행렬은 간선이 100개든 600개든 50×50칸을 그대로 쓰므로 Case 3과 4가 10,604바이트로 똑같다. 반면 인접 리스트는 간선 하나당 노드 2개(16바이트)를 쓰므로 희소 6,408바이트, 밀집 34,408바이트로 5배 넘게 벌어진다. 희소에서는 리스트가 행렬보다 가볍지만 밀집에서는 3배 이상 무거워진다. Kruskal 쪽에는 간선 배열과 정렬용 임시 배열, Union-Find도 포함되는데, 간선 배열이 간선 수에 비례해 커지는 것도 밀집에서 불리하게 작용했다.

**실행시간: 밀도에 따라 유불리가 뒤집힌다.** Kruskal은 희소에서 2.49μs로 가장 빨랐지만 밀집에서 15.70μs로 6배 이상 느려졌다. Kruskal의 비용은 간선 수 E에 좌우되기 때문이다(정렬이 O(E log E)). 간선이 6배가 되면 정렬할 양도 6배가 된다. 반대로 Prim은 희소 4.96μs, 밀집 5.53μs로 거의 차이가 없었다. 인접 행렬 기반 Prim은 매 단계에서 key 배열 전체를 훑어 최솟값을 고르므로 **간선 수와 무관하게 O(V²)**이고, V가 50으로 고정이라 간선이 늘어도 일이 거의 안 늘어난다.

**그래프 밀도의 영향.** 희소 그래프에서는 Kruskal이 Prim보다 2배 빠르고 메모리도 적게 써서 모든 면에서 유리했다. 밀집 그래프에서는 반대로 Prim이 3배 빠르고 메모리도 3분의 1이었다. 즉 **E가 V²에 가까워질수록 행렬+Prim이, E가 V에 가까울수록 리스트+Kruskal이 유리하다.** 이론적으로도 Kruskal은 O(E log E), 행렬 Prim은 O(V²)이므로, E가 V²/log V 근처를 넘어가면 Prim이 앞선다는 점과 실험 결과가 맞아떨어진다.

**정리.** 실제 그래프는 대부분 희소하므로 Kruskal(또는 우선순위 큐를 쓰는 Prim)이 널리 쓰인다. 다만 간선이 촘촘하고 정점 수가 크지 않다면, 구현이 간단하고 간선 수에 영향받지 않는 인접 행렬 + Prim이 더 나은 선택이 된다.

실행시간은 최적화 옵션과 환경에 따라 달라진다. 위 값은 `-O2`로 컴파일한 결과이며, Visual Studio의 Debug 빌드에서는 더 크게 나온다. 네 경우를 같은 조건에서 비교하는 것이 중요하다.
